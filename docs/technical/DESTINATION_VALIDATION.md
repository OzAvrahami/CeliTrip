## Implemented behavior

Destination creation/editing now starts with one chosen source language (Hebrew, English, French or Russian). Leaving the source field, pressing Enter, or choosing **Find names** commits a lookup; keystrokes alone do not send requests. The three other names remain editable. Exact unique matches can populate automatically; multiple candidates require **Use this destination**. Countries retain Wikidata identities; city candidates are constrained by the saved parent country's identity and display descriptions plus administrative-region labels to distinguish matches. Missing labels remain empty, with no language fallback masquerading as a translation. The bounded lookup supports common city/town/municipality classes, not every geographic entity in Wikidata; unsupported or ambiguous places require refinement/manual input. Geographic data does not establish CeliTrip launch coverage or venue evidence.

The shared server translation service accepts only the selected text, source locale and target locales. It never sends notes, sessions, credentials or whole records. Fixed provider origins, bounded input, timeouts and a per-actor database throttle limit requests. Wikidata lookup works without a key. The DeepL text adapter is integrated but **not operationally validated**: no provider/key exists in local configuration. Missing configuration returns an explicit error and no generated success. Unit tests inject clearly synthetic provider responses solely to test the adapter contract. See [secure setup](../development/LOCAL_DEVELOPMENT.md#destination-names-and-publication).

Immutable generation receipts store the provider, source hash, actor, base revision and returned names/identity. Saved destination revisions attach provenance and the source revision to generated values. Manual and reviewed values are protected during regeneration; edits made while a request runs also survive. Both client source tokens and server revision/version checks reject stale generation. Source/translation edits create a new draft and invalidate dependent reviews; generation is never approval. Existing content editors can reuse `translationService().translate({source, sourceLocale, targets})` server-side for explicitly selected public fields; automatic generation buttons were added only to destination forms in this task.

Destination storage extends existing entities, catalog rows, sessions, roles, transactions and audit services. An additive migration initializes private revision snapshots of existing catalog names, retaining original publication pointers and records. Established Italy/Rome geographic identities are recorded without altering names or granting review approval. `state` remains archival state; `review_state`, revision/cycle and the pinned publication are separate. New drafts have no publication. Explicit submit, subject review, four language reviews, return, saved-revision preview, local publish, withdraw, archive and restore actions use server authorization and optimistic concurrency. Revoked reviewers cannot satisfy publication gates. Parent countries must be published before child destinations; referenced parents cannot be archived, and parents with published children cannot be withdrawn.

Destination access reuses scoped roles. In this guarded fictional environment only, an existing catalog administrator may use their separately assigned Rome demo roles on catalog destinations outside Rome. Administrator status alone does not create subject, language or publisher authority. Language grants remain locale-specific. No grants, account credentials, MFA material or local password exception boundaries were changed.

New public destination pages use `/{locale}/destinations/{stable-local-id}` and read only pinned, published revisions with published ancestors. These are minimal fictional name pages, not new destination discovery guides. Branch reads outside Rome are also suppressed while their destination hierarchy is unpublished. The accepted Rome route and fixture publication remain intact. Draft or withdrawn routes show the not-found state and noindex; Next.js streaming can return HTTP 200 for that not-found UI, so HTTP validation checks the actual response content rather than assuming every not-found response has status 404.
